This page has two kinds of numbers:

- **HTTP benchmarks** — tileserver-rs and its alternatives run in Docker and serve the same fixtures under the same load. These are the numbers to compare servers with.
- **In-process benchmarks** — criterion micro-benchmarks of single hot functions (further down). These show where time goes inside tileserver-rs; they do not compare servers.

## Test environment

Run captured **2026-10-16** against `tileserver-rs:latest` built from `main` at commit `cff03152` (after v2.38.0, with CEL filtering and the LLM proxy).

- **Hardware**: Apple Silicon MacBook, 12 cores, Docker Desktop (ARM64 native images)
- **Load tool**: [autocannon](https://github.com/mcollina/autocannon), 100 connections, 10 s per case (STAC: 20 connections, 30 s warmup)
- **Competitors**: `ghcr.io/maplibre/martin:latest`, `maptiler/tileserver-gl:latest`, `ghcr.io/developmentseed/titiler:latest`
- **Quiet host**: each group started only after `benchmarks/scripts/run-quiet.sh` measured the host as idle for 15 s (non-Docker processes under 120 % of one core in total, benchmark containers under 20 %, at least 25 % memory free). The measured load before and after every group is in the run's `stability.log`.
- **Errors**: 0 non-2xx responses in every case below.

::alert{type="warning"}
The load client runs on the same machine as the servers, so absolute req/s values are machine-specific. Compare the **ratios** between servers, not the raw numbers with another machine. After the OGC and STAC groups the host check saw a `node` process at 113–155 % CPU; those two groups started on a quiet host but may have been disturbed while they ran.
::

### Read this before comparing PMTiles and MBTiles

The stored tiles are gzip-compressed. The PMTiles and MBTiles groups send **no** `Accept-Encoding` header:

- tileserver-rs and tileserver-gl send the stored gzip tile (Florence z12: **58 KB**, `content-encoding: gzip`).
- martin decompresses and sends the raw tile (Florence z12: **82 KB**, no `content-encoding`).

So these two groups do not measure the same work. The compression group sends an explicit `Accept-Encoding` to every server, so it compares equal work:

| Encoding | tileserver-rs | martin | tileserver-gl |
| -------- | ------------- | ------ | ------------- |
| identity (82.93 KB) | 1,867 req/s · 52.9 ms | 1,866 req/s · 52.8 ms | sends gzip anyway |
| br (60.5 KB) | 1,475 req/s · 70.3 ms | 1,477 req/s · 68.5 ms | sends gzip anyway |
| zstd (64.6 KB) | 1,386 req/s · 73.5 ms | 1,395 req/s · 72.0 ms | sends gzip anyway |
| gzip (61.8 KB) | 1,388 req/s · 73.3 ms | 1,462 req/s · 70.4 ms | 1,407 req/s · 72.7 ms |

At the same encoding tileserver-rs and martin are within 1 % (gzip: 5 %). tileserver-rs caches brotli and zstd variants per `(source, z, x, y, encoding)`, so re-encoding cost is paid once per tile. The April 2026 result where martin fell to 107 req/s on brotli does not hold with the current martin image.

## Running benchmarks

```bash
# Build the image from your checkout
docker build -t tileserver-rs:latest .

# Start every server (tileserver-rs, martin, tileserver-gl, titiler, PostGIS)
docker compose -f benchmarks/docker-compose.yml --profile all up -d

# Build the world COG fixture once (needs GDAL)
benchmarks/scripts/make-benchmark-cog.sh

# Run all groups, each only when the host is quiet
benchmarks/scripts/run-quiet.sh

# Turn a run into markdown tables
node benchmarks/scripts/summarize-run.mjs benchmarks/results/<timestamp>
```

Run single groups directly with the harness:

```bash
cd benchmarks
node run-benchmarks.js --type pmtiles            # or mbtiles, postgres, postgres_function,
                                                 # cog, dem, raster, ogc, stac, compression
node run-benchmarks.js --type cog --server tileserver-rs
node run-benchmarks.js --duration 30 --connections 200
node run-benchmarks.js --markdown
```

With pnpm 12, pass flags without `--`: `pnpm --filter @tileserver-rs/benchmarks run bench --type pmtiles`.

Quit heavy applications first and check `stability.log` after the run. A result measured on a busy host is not a valid result.

## Optimization Tips

1. **Use release builds** - `cargo build --release` is 10-50x faster than debug
2. **Use PMTiles for production** - cloud-native, HTTP range request friendly
3. **Use MBTiles for development** - easy to generate and inspect with SQLite tools
4. **Enable compression** - gzipped tiles reduce bandwidth significantly
5. **Use CDN caching** - tiles are immutable, cache with long TTLs
6. **Match connections to cores** - more connections than CPU cores adds overhead
7. **For COG serving** - use internal tiling and overviews for faster access

## Raster fast-path (STAC mosaic, band math)

Added in the `raster` fast-path stack (commits #1-#8 merged into `main` 2026-04-19).  Measured on a 12-core Apple M2 / 16 GB with the `raster` feature enabled and the default CPU baseline (`x86-64-v3` via the `-fast` Docker tier rebuilds these with AVX-512 / SVE2).

Reproduce with:

```bash
cargo bench --bench raster --features raster
```

| Benchmark | Median time | What it measures |
|-----------|-------------|-------------------|
| `raster_encode_256/png` | 216 µs | RGBA → PNG encode at the HTTP boundary. |
| `raster_encode_256/jpeg_q85` | 715 µs | RGBA → JPEG q=85. |
| `raster_encode_256/webp_lossless` | 280 µs | RGBA → lossless WebP. |
| `raster_decode_png_256` | 131 µs | PNG → `RasterImage` (band-math ingest path). |
| `raster_mosaic_5_assets_256/first` | **115 µs** | 5-layer mosaic, `first` method. Short-circuits once canvas is opaque, so it's 5-20× faster than stats methods. |
| `raster_mosaic_5_assets_256/highest` | 636 µs | Per-pixel max over 5 layers. |
| `raster_mosaic_5_assets_256/lowest` | 644 µs | Per-pixel min over 5 layers. |
| `raster_mosaic_5_assets_256/mean` | 1.38 ms | Per-pixel arithmetic mean. |
| `raster_mosaic_5_assets_256/median` | 2.58 ms | Per-pixel median (retains all layers, sorts per-pixel). Heaviest; use only when outlier robustness matters. |
| `raster_mosaic_5_assets_256/stdev` | 1.49 ms | Per-pixel standard deviation. |
| `raster_mosaic_5_assets_256/count` | 214 µs | Per-pixel count of valid contributions. |
| `raster_band_math_ndvi_256` | 1.52 ms | Pure-Rust NDVI `(b2-b1)/(b2+b1)` over a 256×256 two-band raster. |

### Comparison to titiler

Titiler's own benchmarks (from [titiler#321](https://github.com/developmentseed/titiler/issues/321) and rio-tiler's internal criteria tests) place equivalent in-memory operations in the same order of magnitude: ~1-3 ms for NDVI on a 256×256 tile, dominated by numpy+numexpr overhead.  tileserver-rs lands in the same envelope with `exmex` (pure-Rust, ~1.5 ms) without the Python import cost; switching to an AVX-512-targeted build (`:fast` Docker tier) cuts these further on servers with the right CPU.

### Why COG serving is fast

The COG results in the HTTP table above come mainly from **overview pyramid selection**: GDAL is opened with `OVERVIEW_LEVEL=N`, so the warp reads a pre-computed overview instead of the full-resolution raster. Other contributors: a pool of cached `Dataset` handles per file and overview level, so concurrent tiles render in parallel without reopening the file ([open-dataset cache](/getting-started/config#open-dataset-cache)), parallel mosaic compositing with `futures::join_all`, and the `RasterImage` ndarray pipeline that keeps pixel values as floats through the mosaic layer.

### What was not yet benchmarked

- **Cold-path STAC `/search` + `/vsicurl/` COG fetch**: dominated by network RTT, not CPU.  Typical 500-2000 ms on Element84 Earth Search; this is *not* part of the raster fast-path scope.
- **Full mosaic pipeline with real COG reads**: requires a live S3 COG and a local network, so the cold-path numbers are deferred to `benches/stac_live.rs` in a follow-up commit.
- **GDAL Dataset moka cache hit rate**: qualitative observation on demo.tileserver.app shows warm-path tiles dropping from ~2 s to ~150 ms after the cache lands, matching the arithmetic (`~30 ms × 5 asset re-opens = 150 ms saved` per tile).

## Style-rewrite hot path

`rewrite_style_for_api` runs once on every `GET /styles/{id}/style.json` and again before every native-render request — it converts relative tile/source URLs to absolute, forwards `?key=` query strings, and injects the MLT encoding hint where applicable.

Reproduce with:

```bash
cargo bench --bench styles
```

| Benchmark | Median time | Style fixture |
|-----------|-------------|---------------|
| `style_rewrite/tiny_no_key` | 789 ns | 1 source, 0 layers — synthetic minimal style |
| `style_rewrite/tiny_with_key` | 1.04 µs | Adds `?key=…` rewriting cost to every URL |
| `style_rewrite/protomaps_light_no_key` | 7.37 µs | Real-world Protomaps Light (4 sources, 80 layers) |
| `style_rewrite/protomaps_light_with_key` | 7.78 µs | Same style with `?key=` forwarding |

Sub-10 µs per call confirms style rewriting is not on the critical path of perceived latency — it's at least three orders of magnitude faster than the actual tile fetch (1-10 ms range).

## MVT→MLT transcode (native mlt-core 0.11 reader)

When a client requests `.mlt` from an MVT source, `mvt_to_mlt` transcodes on the fly. As of mlt-core 0.11 this uses the native `mvt::mvt_to_tile_layers` reader, which decodes MVT straight into row-oriented `TileLayer`s — replacing the previous hand-rolled GeoJSON `FeatureCollection` bridge with its own column-type inference.

Reproduce with:

```bash
cargo bench --features mlt --bench mlt -- mvt_to_mlt_transcode
```

| Zoom | Bridge (before) | Native (after) | Change | Throughput |
|------|-----------------|----------------|--------|------------|
| z0 | 15.59 ms | 16.67 ms | +6.95% | 5.06 → 4.73 MiB/s |
| z4 | 184.6 ms | 142.3 ms | **−22.9%** | 9.51 → 12.34 MiB/s |
| z7 | 230.2 ms | 183.2 ms | **−20.4%** | 7.65 → 9.61 MiB/s |
| z13 | 19.72 ms | 15.89 ms | **−19.5%** | 23.68 → 29.40 MiB/s |

Real-data tiles (z4/z7/z13) transcode ~20-23% faster because the native reader skips the intermediate GeoJSON allocation and hand-rolled type inference. The trivial z0 world-overview tile regresses ~7% — its near-empty payload is dominated by the reader's fixed setup cost, so there is nothing to amortise. All deltas are statistically significant (p < 0.05). Both sides run mlt-core 0.11.0, so this isolates the reader change rather than the version bump. Absolute timings are machine-specific (measured on Apple Silicon, `--release`); the percentage deltas are the portable signal.

## In-process benches at a glance

The crate ships ten criterion benches that exercise pure-function hot paths across every feature without an HTTP harness. All are reproducible from a clean checkout:

```bash
cargo bench --bench cache                       # tile cache lookups
cargo bench --bench cog --features stac         # COG path classification (vsicurl/vsis3)
cargo bench --bench duckdb --features duckdb    # tile→bbox + SQL template substitution
cargo bench --bench frontend                    # MIME guessing + cache-control rule
cargo bench --bench geoparquet --features geoparquet # tile→bbox (plain + buffered)
cargo bench --bench mlt --features mlt          # MLT parse / decode / transcode
cargo bench --bench postgres --features postgres # geometry-type + JSON Schema mapping
cargo bench --bench raster --features raster    # raster encode / mosaic / band math
cargo bench --bench stac --features stac        # bbox merging + URL classification
cargo bench --bench styles                      # style.json URL rewriting
```

Why these ten: they cover the per-request work that runs **inside** the Tokio worker — between when the router dispatches and when bytes are written back to the socket. Network, Postgres round-trips, and disk reads are excluded by design (those are measured in the `benchmarks/` HTTP harness). Every cargo feature flag now has at least one corresponding bench so contributors can verify their changes haven't regressed any feature's hot path.
