---
title: CEL Feature Filters
description: Filter the features inside vector tiles at request time with CEL expressions, for every source type including PostGIS.
---

tileserver-rs can drop features from a vector tile before it is sent. You
write the rule as a [CEL](https://github.com/google/cel-spec) (Common
Expression Language) boolean expression. CEL is the same language that
Kubernetes admission policies and Envoy use.

The filter works on every vector source: PMTiles, MBTiles, `dir`, `tar`, cloud
PMTiles, MLT sources, and PostGIS tables and functions. You do not need to
rebuild the tileset.

## Per request: `?filter=`

Add a URL-encoded CEL expression to the tile URL:

```bash
# Only residential landuse features
curl "http://localhost:8080/data/openmaptiles/14/8192/5461.pbf?filter=type%3D%3D'residential'"
```

The server evaluates the expression once for each feature:

- If the result is `true`, the feature stays in the tile.
- If the result is `false`, or the expression fails (for example a missing
  property), the server drops the feature.
- If a layer has no features left, the server removes the layer.
- If no layer is left, the response is `204 No Content`.

The `.mvt`, `.pbf` and `.mlt` endpoints accept `?filter=`, and so do composite
ids such as `roads+water`.

## Per source: a preset

A preset filter applies to every tile that the source serves. The server never
serves a source with a preset unfiltered, so you can use a preset to isolate
data.

```toml
[[sources]]
id = "openmaptiles-residential"
type = "pmtiles"
path = "/data/openmaptiles.pmtiles"

[sources.filter]
expression = "type == 'residential' || type == 'commercial'"
applies_to_layers = ["landuse"]  # only filter these layers; others pass through
```

PostGIS tables and functions accept the same `filter` table:

```toml
[[postgres.tables]]
id = "buildings"
table = "buildings"

[postgres.tables.filter]
expression = "height > 50"
```

If a source has a preset and the request also has `?filter=`, the server
combines the two with a logical AND.

The server compiles every preset when it loads the config. If an expression
does not compile, startup fails with an error that names the source.

## Expression examples

Each feature property is available as a CEL variable with the same name.

```cel
// Boolean over properties
type == 'residential'

// Numeric comparison
height > 50 && levels >= 5

// String matching
name.startsWith('St ')

// Membership
class in ['motorway', 'trunk', 'primary']

// Optional property: true only when `ele` exists and is high
has(ele) && ele > 1000

// Combined
type == 'building' && height > 100 && name.matches('.+ Tower$')
```

Property values map to CEL types as follows:

| MVT type                                | CEL type                    |
| --------------------------------------- | --------------------------- |
| `string`                                | `string`                    |
| `bool`                                  | `bool`                      |
| `int`, `sint`                           | `int`                       |
| `uint`                                  | `int` (`uint` above 2⁶³−1)  |
| `float`, `double`                       | `double`                    |

## Allowed functions

The filter runs in a sandbox. An expression can use only these functions:

- comparison, arithmetic and logical operators, `in`, `[]` and `?:`
- the macros `has`, `all`, `exists`, `exists_one`, `map` and `filter`
- `size`, `contains`, `startsWith`, `endsWith` and `matches`
- the conversions `int`, `uint`, `double` and `string`

If an expression uses any other function, compilation fails. This includes
`timestamp`, `duration`, `dyn` and `type`. No expression can read the
filesystem, the network, the process environment or the clock. An expression
can be at most 4096 bytes long.

## Errors

An invalid expression returns `400 Bad Request`. The message gives the line
and column of the error:

```text
invalid filter: ERROR: <input>:1:9: Syntax error: mismatched input '<EOF>'
```

## Caching and metrics

- The server compiles each unique expression once and keeps it in a
  process-wide compile cache.
- The tile cache stores each filtered tile under its own key: source, z/x/y,
  encoding and filter hash. A filtered tile never replaces the unfiltered tile.
- The `cel_filter_compile_total{result="hit"|"miss"}` counter on the
  Prometheus endpoint (`/metrics`) counts compile-cache hits and misses.

## Build

The filter is in the `cel` cargo feature. A default build includes it. To
build without it:

```bash
cargo build --release --no-default-features --features postgres,raster,mlt,cloud,stac,dem
```
